# Архитектура Scam Weather

Nov 21, 2026 · @Iskander

## Обзор

Scam Weather — сеть, в которой банк жертвы BEC за секунды предупреждает банк получателя, пока деньги ещё лежат на счёте дропа. Оркестратор пересылает сигналы между банками, но не может ни прочитать, ни подделать их.

**Сценарий первой версии.** Банк A подтверждает BEC-кейс: деньги клиента ушли на счёт X. Он публикует сигнал «счёт X — подозрение на дропа». Банк B, где открыт счёт X, замораживает исходящие переводы. Банк C, чей клиент собирается платить на тот же счёт, отправляет платёж на проверку.

**Три принципа архитектуры:**

1. Всё чувствительное делается внутри банка. Нормализацию, хэширование, подпись и шифрование выполняет узел банка в его контуре.
2. Оркестратор пересылает только шифротекст. Он видит конверт (кто, кому, тип, срок), но не содержимое.
3. Devin пишет код решений заранее, но не принимает решения. В момент платежа работает детерминированный код банка.

## Компоненты и топология

У каждого банка свой узел внутри его контура, а оркестратор только пересылает шифротекст. Банки сами подключаются наружу по mTLS, входящие порты не нужны. Это знакомая банкам модель: у SWIFT банк тоже ставит у себя шлюз.

&#91;embedded content: топология · 3 узла банков и слепой оркестратор\]

Банк A сам хэширует, подписывает и шифрует сигнал; банки B и C забирают его и применяют каждый свою политику.

**Три варианта оркестратора.** На хакатоне выбираем A, архитектура позволяет перейти на B, если банки потребуют.

| Вариант | Что видит центр | Плюсы | Минусы | Когда |
| --- | --- | --- | --- | --- |
| A. Слепой посредник | Конверт: кто, кому, тип, срок | Только исходящие соединения, сообщения ждут офлайн-банк | Видны метаданные | Хакатон и пилот |
| B. Прямой обмен банк–банк | Только реестр | В центре ничего не хранится | Входящий порт у каждого банка, N² соединений | Если банки потребуют |
| C. Запрос в момент платежа | Сами запросы | Минимум передаваемых данных | Задержка в пути платежа | Дополнение для крупных сумм |

## Протокол событий

Каждое событие — это открытый конверт для маршрутизации, зашифрованное содержимое и подпись банка-отправителя. Оркестратор работает только с конвертом.

**Что хранит оркестратор:**

```json
{
  "envelope": {
    "signal_id": "sig_0192",
    "revision": 1,
    "issuer": "bank-a",
    "audience": "group-uae-bec",
    "kind": "bec_beneficiary",
    "expires_at": "2026-11-22T08:00Z",
    "prev_hash": "9f3c…e1"
  },
  "payload": "eyJhbGciOiJFQ0RILUVTIiwi…",
  "signature": "ed25519:4b1a…c7"
}
```

**Что видит банк-получатель после проверки подписи и расшифровки:**

```json
{
  "indicator": { "type": "account_hmac", "value": "hmac:7d2e…a0" },
  "evidence_level": "issuer_analyst_verified",
  "reason_code": "confirmed_bec_case",
  "amount_band": "100k-500k",
  "first_seen": "2026-11-21T07:52Z"
}
```

**Минимизация данных.** Узел отправителя проверяет схему до шифрования. Поле, которого нет в схеме, узел не отправит. После шифрования оркестратор содержимое проверить не может.

| Уходит из банка, зашифровано | Не уходит никогда |
| --- | --- |
| HMAC(ключ группы, IBAN) | IBAN, имена, ИНН, KYC |
| Тип сигнала и код причины | Балансы, выписки, история операций |
| Уровень доказанности | Точные суммы |
| Диапазон суммы, срок, версия | Свободный текст и вложения |

**Жизненный цикл сигнала.** Публикация (v1) → доставка → подписанный ACK → исправление (v2) или отзыв → истечение срока. Узел хранит максимальную применённую версию, поэтому старая версия не воскрешает отозванный сигнал.

**API оркестратора:**

| Метод | Назначение |
| --- | --- |
| `POST /v1/signals` | Публикация подписанного конверта. Ключ идемпотентности привязан к банку |
| `POST /v1/signals/{id}/revisions` | Исправление или отзыв (RETRACT), только автором сигнала |
| `GET /v1/inbox?after={cursor}` | Узел сам забирает свои события по курсору |
| `POST /v1/inbox/{delivery_id}/ack` | Подписанный ACK: applied, obsolete, expired или invalid |
| `POST /v1/signals/{id}/feedback` | Обратная связь без данных клиента |

## Безопасность канала

Пять механизмов делают оркестратор «слепым»: даже при его взломе сигналы нельзя прочитать или подделать.

| Механизм | Как работает | Что даёт |
| --- | --- | --- |
| Подпись отправителя | Ed25519 / JWS на каждом событии, получатель проверяет сам | Оркестратор не может подделать или изменить сигнал |
| Шифрование для получателей | HPKE / JWE под публичные ключи банков из группы | В базе оркестратора только шифротекст |
| Сопоставление по хэшу | HMAC(ключ группы, нормализованный IBAN), ключа нет у оркестратора | Совпадение счёта без раскрытия IBAN |
| Журнал с цепочкой хэшей | Каждая запись содержит хэш предыдущей, ACK подписаны получателем | Доказуемо, кто, что и когда получил |
| Только исходящие соединения | Узел банка сам подключается по mTLS | Банку не нужен входящий порт |

**Модель угроз:**

| Угроза | Защита |
| --- | --- |
| Взломан оркестратор | Подпись отправителя и шифрование под получателя: нельзя ни прочитать, ни подделать |
| Перехват трафика | mTLS с сертификатами организаций от CA консорциума |
| Повтор старого события | Версия, nonce и срок годности; узел хранит максимальную применённую версию |
| Участник перебирает IBAN по хэшам | Узкие группы, ротация ключа, лимит и журнал сравнений; в пилоте PSI |
| Спор «мы этого не получали» | Подписанный ACK и журнал с цепочкой хэшей |
| Ошибочный сигнал блокирует честных клиентов | Срок годности, отзыв, режим «только наблюдать», решение за банком |
| Утечка ключей | Ключи в HSM или vault банка, ротация, отключение участника одним действием |
| Данные уехали из страны | Узел и шифрование внутри банка, оркестратор можно разместить в ОАЭ |

HMAC — защита для демо. Любой участник группы с ключом может проверить наличие конкретного IBAN в сигналах, поэтому в пилоте его заменяет PSI.

## Маппер событий

Маппер превращает событие сети в решение конкретного банка и состоит из трёх слоёв внутри узла. Тот же путь работает в обратную сторону: подтверждённый внутренний кейс становится событием для сети.

| Слой | Что делает | Кто пишет |
| --- | --- | --- |
| 1. Адаптер формата | Общая схема ↔ формат банка (JSON, ISO 20022 `pacs.008`, CSV), нормализация IBAN | Devin |
| 2. Политика банка | Тип сигнала × уровень доказанности × роль счёта → действие | Черновик — Devin, утверждает Fraud Risk банка |
| 3. Интеграция | Запись в движок правил, Kafka или систему кейсов банка | Devin |

Нормализация IBAN критична: если два банка нормализуют счёт по-разному, хэши не совпадут и сигнал не сработает.

**Пример политики банка B.** Один и тот же сигнал даёт разные действия в зависимости от роли счёта в банке.

```yaml
# policy.yaml банка B — владелец Fraud Risk, Devin только предлагает изменения
on_signal: bec_beneficiary
rules:
  - when: { account_role: own_customer, evidence: issuer_analyst_verified }
    action: freeze_outgoing     # счёт нашего клиента похож на дропа
    open_case: true
    max_duration_h: 24
  - when: { account_role: payee_of_own_customer }
    action: review              # наш клиент собирается платить на этот счёт
  - when: { evidence: suspected }
    action: score_plus_30       # слабый сигнал только повышает риск
default: no_effect
expired_or_retracted: no_effect
```

Решение о платеже всегда принимает политика самого банка, а не сеть.

## Роль Devin

Devin работает на этапе разработки и пишет код узлов банков. В момент платежа решение за миллисекунды принимает детерминированный код банка. Внешнего агента в платёжном контуре нет.

| Когда | Что получает Devin | Что выдаёт |
| --- | --- | --- |
| Подключение банка | Спецификацию API или примеры данных банка, SDK узла, шаблон политики, проверки на соответствие | Адаптер, интеграцию, черновик политики, тесты, PR в репозиторий банка. Прогон в песочнице Daytona |
| Банк поменял формат | Упавшие проверки на соответствие | PR с исправлением адаптера |
| Новый тип сигнала в сети | Обновлённую общую схему | PR во все узлы с черновиком политики для каждого банка |
| Пропущенный кейс | Новую карточку кейса | Предложение по политике и тест |

**Проверки на соответствие** — общий набор тестов, который обязан пройти каждый узел. В него входят карточки BEC-кейсов из `bec-cases/` и проверки безопасности: поддельная подпись отклонена, старая версия не применяется, лишнее поле не уходит.

**Аргумент для питча.** Главный барьер таких сетей — интеграция каждого банка. Devin превращает подключение банка из проекта на месяцы в PR, который проходит общий набор проверок.

## Реализация на хакатоне

Демо — один TypeScript-проект: оркестратор, общий SDK узла и три симулятора банков с разными форматами данных.

| Компонент | Реализация |
| --- | --- |
| Оркестратор | HTTP API, SQLite, журнал с цепочкой хэшей, опрос раз в секунду |
| SDK узла | Подпись Ed25519, шифрование JWE, HMAC, проверка схемы, ACK (библиотека `jose`) |
| Банк A | JSON, публикует сигнал из подтверждённого BEC-кейса |
| Банк B | Свой JSON с другими полями, политика freeze\_outgoing |
| Банк C | ISO 20022 XML, коннектор пишет Devin, политика review |
| Интерфейс | React: панели банков, вид базы оркестратора, журнал |

**Сценарий демо на 5 минут:**

1. 0:00 — в банке A подтверждён BEC-кейс: $123 тыс. ушли на счёт X.
2. 0:40 — узел банка A подписывает, шифрует и отправляет сигнал.
3. 1:20 — банк B замораживает исходящие с счёта, банк C отправляет платёж своего клиента на проверку.
4. 2:10 — показываем базу оркестратора: только шифротекст. Меняем байт сигнала — узел отклоняет подпись.
5. 3:00 — PR от Devin: банк D подключён, проверки зелёные.
6. 3:50 — банк D сразу получает и применяет сигнал.
7. 4:30 — банк A отзывает сигнал, сеть снимает его влияние.

Сессия Devin длится минуты, поэтому заранее завершённый прогон и записанное видео обязательны.

## Ответы на ревью банковской инфраструктуры

Ревью от инженера, который работает с банковскими переводами, подняло шесть вопросов. Ниже ответы, которые теперь входят в архитектуру.

### Тайминг: мы не останавливаем тот же самый платёж

Остановить SWIFT-перевод (`pacs.008`), который уже принят и исполнен, нельзя. Поэтому сигнал описывает **счёт**, а не конкретную операцию, и у защиты три точки вмешательства:

| Когда | Где | Что происходит |
| --- | --- | --- |
| До отправки | Банк A, следующая жертва | Счёт уже есть в сигналах. Узел банка A сверяет HMAC получателя с локальным кэшем до формирования `pacs.008`, антифрод банка A ставит платёж на проверку |
| При поступлении | Банк B | Входящий `pacs.008` идёт на помеченный счёт. Антифрод банка B зачисляет деньги, но блокирует исходящие с этого счёта |
| После исполнения | Банк B | Деньги уже у дропа. Банк B замораживает исходящие до обналички и запускает возврат через `camt.056` или gpi Stop and Recall |

Первую жертву сеть чаще всего не спасает. Она защищает следующих жертв и перехватывает обналичку.

### Hub не стоит на пути платежа

Сигналы рассылаются заранее и хранятся в контуре каждого банка. В момент платежа идёт сверка с локальной копией, без сетевого запроса в Hub. Hub не добавляет задержку в SWIFT или во внутренние переводы и не становится точкой отказа: если он недоступен, банки работают с последним полученным набором сигналов.

### Что зашифровано

Шифруется полезная нагрузка: HMAC счёта, код причины, уровень доказанности, диапазон суммы, время первого обнаружения. В открытом виде остаётся только конверт: отправитель, группа получателей, тип сигнала, версия, срок жизни.

### Почему банк может доверять сигналу

- Каждый сигнал подписан ключом банка-участника. Участники входят в консорциум со своей системой сертификатов.
- Сигнал — это не команда. Действие выбирает политика банка-получателя по типу сигнала и уровню доказанности.
- За ложный сигнал отвечает отправитель по соглашению участников. Сигнал можно отозвать.

### Обновления сигнала

У сигнала есть версии, отзыв и срок жизни. Узел применяет только максимальную версию, поэтому устаревшая версия не может вернуть отозванный сигнал.

### Регуляторика

В каждой юрисдикции свои правила (ЦБ, ОАЭ, ЕС). Узел в контуре банка и слепой Hub упрощают разговор с регулятором, потому что данные клиентов не покидают банк. Юридическое заключение по каждой стране всё равно нужно до пилота.

### Devin как часть продукта

Подключение банка Б:

```
Общий контракт сигнала + тестовая схема банка Б
  → Devin пишет коннектор и тесты
  → черновой PR
  → инженер банка проверяет и выпускает коннектор
```

Проверка платежа:

```
Банк А подтверждает инцидент
  → коннектор А отправляет минимальный сигнал
  → Hub доставляет его банку Б
  → коннектор Б сопоставляет сигнал с локальным платежом
  → антифрод банка Б решает, нужна ли дополнительная проверка
```

Когда банк выпускает новую версию своей схемы, Scam Weather запускает сессию Devin через API и возвращает инженеру черновой PR с обновлённым коннектором и результатами тестов. Для демо тот же шаг выполняется в Devin вручную: ему нужны тестовый репозиторий, согласованная схема и синтетические примеры.

| Вопрос | Ответ |

## Открытые вопросы и путь к пилоту

Самый большой риск — не техника, а согласие двух банков на один сценарий и юридическая схема обмена.

| Риск | Влияние | Что делаем |
| --- | --- | --- |
| Банки не готовы подключаться | высокое | Слепой оркестратор и подключение через Devin снижают цену входа; до разработки пилота получить согласие двух владельцев антифрода |
| Право на обмен через посредника | высокое | Согласовать роль оркестратора с legal и privacy до реальных данных (ОАЭ: декрет-закон № 6/2025, ст. 147 и 149) |
| Ошибочный сигнал задерживает честные платежи | высокое | Срок годности, отзыв, старт в режиме «только наблюдать» |
| Перебор IBAN по HMAC | среднее | Лимиты и журнал сравнений, затем PSI |

**Открытые вопросы:**

- Вариант A (слепой посредник) или B (прямой обмен) — что допустят службы безопасности банков?
- Кто владеет ключом группы HMAC и как часто его ротировать?
- С какого момента кейс можно публиковать, и кто в банке утверждает публикацию?
- Какой срок жизни сигнала по умолчанию: 24 часа в демо, в пилоте по типу сигнала?

**Путь к пилоту:** согласие двух банков → юридическая схема → ретроспективная проверка на истории → режим «только наблюдать» → ограниченный запуск на одном сценарии.
