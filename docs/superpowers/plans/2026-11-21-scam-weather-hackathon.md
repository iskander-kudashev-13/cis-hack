# Scam Weather · план реализации на 3 часа

**Окно — 12:30–15:30 по Дубаю, 21 ноября 2026.** Цель — подать работающий локальный прототип и видео к 15:30. В расписании сдача в 16:00, живое демо пяти лучших команд в 16:30, по пять минут без Q&A. Последние 30 минут до дедлайна держим как резерв. [Форма сдачи](https://docs.google.com/forms/d/e/1FAIpQLSf7M9M4UwJUGBRnblfGOhNoH0ffnJDZcrgylvRCyeTvNojC1A/viewform)

**Результат** — два банковских симулятора на одном экране. Банк A публикует временное предупреждение, Bank B получает его через ленту и отправляет совпавший перевод на дополнительную проверку. Отзыв сигнала снимает его влияние на новые попытки. Контрольный перевод проходит на всех этапах.

**Архитектура** — React + TypeScript + Vite и один локальный API на Node.js. Три части с отдельным состоянием: Bank A, hub и Bank B. Bank B читает свою ленту раз в секунду, применяет событие локально и подтверждает обработку. Для первого сквозного прогона используйте состояние в памяти и явный Reset. SQLite добавляйте только при готовой сборке и запасе до заморозки. Это отступление от первоначального брифа ради хакатонного окна.

**Исходная спецификация** — [бриф Scam Weather](../../SCAM-WEATHER-BUILD-BRIEF.md). Репозиторий на момент проверки содержал README, лицензию и документацию. Названия будущих модулей и команд ниже задают контракт для реализации.

## 2. P0 · ядро, которое видно на демо

1. **Публикация.** У Bank A три подготовленных подтверждённых кейса, связанных одним синтетическим получателем. Кнопка **Publish signal** создаёт сигнал v1. Hub пишет событие и доставку для Bank B. Срок — 24 часа от публикации по часам сервера.
2. **Доставка.** Bank B читает адресованную ему ленту, сохраняет актуальную версию и отправляет ACK. В панели A появляется **Applied by Bank B** только после ACK. Пока его нет, отображается **Awaiting acknowledgement**.
3. **Локальное решение.** Bank B сравнивает получателя выбранной операции с активным сигналом. Совпадение даёт **Review required**, имитация списания отсутствует. Без совпадения локальная политика демо возвращает **Approved**. Hub передаёт сигнал и журналирует доставку, Bank B вычисляет исход.
4. **Отзыв.** **Retract signal** создаёт v2. Bank B применяет отзыв и исключает сигнал из новых решений. Поздний v1 не восстанавливает отметку. Reset возвращает оба банка, ленту, журнал и выбранный кейс в начальное состояние.

**Очередность.** Must — публикация, доставка, совпадение и контроль, отзыв, сброс, наблюдаемый вклад Devin. Should — автоматический опрос и измеренная задержка доставки. Could — SQLite при запасе времени. После 14:20 работаем над стабильностью, записью и сдачей. До первого коммита партнёр проверяет, что выбранный Node запускает Vite. Для нового окружения берите Node 24 LTS. [Требования Vite](https://vite.dev/guide/)

## 3. Синтетические данные и проверка

Два получателя и три кейса банка A достаточны. Значения ниже можно перенести в фикстуру. События публикуются от текущего времени. Тест срока использует подставные часы, чтобы запись можно было повторить в любой момент.

~~~json
{
  "bank_a_cases": [
    {"id": "demo-case-101", "beneficiary_ref": "demo-beneficiary-17", "status": "confirmed"},
    {"id": "demo-case-102", "beneficiary_ref": "demo-beneficiary-17", "status": "confirmed"},
    {"id": "demo-case-103", "beneficiary_ref": "demo-beneficiary-17", "status": "confirmed"}
  ],
  "bank_b_payments": [
    {"id": "demo-match", "recipient_reference": "demo-beneficiary-17", "amount_minor": 2500000, "currency": "AED"},
    {"id": "demo-control", "recipient_reference": "demo-beneficiary-42", "amount_minor": 2500000, "currency": "AED"}
  ],
  "signal": {
    "kind": "suspected_beneficiary_cluster",
    "namespace": "cis-sprint-demo",
    "reason_code": "multiple_related_cases",
    "ttl_seconds": 86400
  }
}
~~~

| Проверка | Как воспроизвести | Ожидаемый результат |
|---|---|---|
| До сигнала | Reset → Run transfer | Испытательный перевод AED 25 000 получает APPROVED |
| Сигнал активен | Publish → дождаться Applied by Bank B → Run transfer | REVIEW_REQUIRED, в журнале видны Bank A и v1 |
| Контроль | Run control при активном сигнале | APPROVED на ту же сумму другому получателю |
| Отзыв | Retract → дождаться ACK v2 → Run transfer | APPROVED по локальной политике стенда |
| Дубликат и порядок | Подать v1 дважды, затем v2 и снова v1 | Одна запись активна до v2. После v2 активной записи нет |
| Срок | Установить тестовые часы ровно на expires_at | Сигнал перестал влиять на решение |
| Граница доступа | Запросить ленту из тестового контекста вне группы | Чужое событие отсутствует |
| Ошибка доставки | Отключить выдачу ленты, подвинуть тестовые часы на 10 секунд, восстановить ленту | Прежний ACK не выдаётся за новый. После 10 секунд UI показывает CHANNEL_STALE, Bank B использует только локальные правила до успешной синхронизации |
| Повторяемость | На втором ноутбуке запустить два прогона с Reset | Одинаковые исходы и читаемый журнал |

Ручные прогоны одного кейса получают отдельные ID попыток. Экран показывает, что это повторная оценка синтетического сценария. После сборки README должен содержать команды, которые действительно запускаются с зафиксированными зависимостями. Закладываем npm ci, npm test, npm run build и документированный старт API и UI. Перед записью выполнить их на втором ноутбуке.

## 4. UI · одна страница, читаемая в записи

~~~text
Scam Weather                           Simulation · 2 banks       [Reset]

Bank A · Fraud analyst                 Bank B · Payment check
3 related cases                        AED 25,000   ·   demo-beneficiary-17
Signal v1 · Expires in 24 hours         APPROVED / REVIEW REQUIRED
[Publish signal] [Retract signal]      Reason · Active signal from Bank A (v1)
Delivery · Applied by Bank B           [Run transfer] [Run control]

Event timeline
12:00:01  Bank A published signal v1
12:00:02  Bank B applied signal v1 · ACK
12:00:04  Transfer sent for review · no simulated debit
~~~

- Слева показываем основание сигнала, справа — что случилось с деньгами. На первом экране помещаются обе карточки и 3–4 последних события. UI на английском, запись 16:9.
- Белый или тёмно-синий фон с высоким контрастом, одна акцентная кнопка на каждом шаге. Зелёный **Approved**, янтарный **Review required**, серый **Retracted**. Всегда показываем текст и причину, цвет помогает считывать статус.
- Пока сигнал доставляется, видны **Awaiting acknowledgement** и полезное действие **Sync inbox** при резервном режиме. После отзыва оставляем обе версии в журнале, актуальный статус меняется после ACK. Кнопка **Reset** всегда доступна для следующего показа.
- Убираем многостраничность, карты, графы, дашборды, настройку ролей и регистрацию. Для питча важны крупный AED 25 000, источник предупреждения и смена исхода. Слайды ограничиваются вступлением, если используете их вообще.
